# Operator view v0

**Open it:** `docs/runs/2026-11-07/lanes/B-operator-view/preview/operator.html` on branch
`operator-view-v0` (a static file; open it in a browser, nothing is deployed).
Regenerate from the repo root:

    python -c "from newsletters.operator import load_operator_view; from newsletters.render import write_operator_preview; write_operator_preview(load_operator_view(['tests/fixtures/operator/fixture-client']), 'docs/runs/2026-11-07/lanes/B-operator-view/preview')"

## What it shows

- A client list with counts per client: Library items, editions, received, sent, pending.
  One row, a **fixture** standing in for Client 1 (there is no real client instance in this repo).
- Per client:
  - **Library:** the same Draft / In Review / Published board the public Library uses,
    and each card opens that surface, rendered by the same `render_surface` function.
  - **Editions:** dated issues, newest first, each with its current gate state.
  - **Interactions:** three columns: received, sent, pending.
- An amber FIXTURE banner on the page and a "fixture data" tag on the client, plus a line
  saying the view is private and not part of the published site.
- Email addresses in interactions are shown as "[email hidden]" (tested).
- Works at phone width (the table scrolls in its own box); checked with
  `check_phone_width.js` in this folder.

## How it is built

- `src/newsletters/operator.py`: typed models (`Client`, `Edition`, `Interaction`,
  `OperatorView`) and `load_client(dir)`, which reads `<dir>/client.json` and never writes.
  Gate states go through the real gate, so Published needs a recorded reviewer.
- At the end of `src/newsletters/render.py`: `render_operator_view` (pure) and
  `write_operator_preview`. These reuse `_board`, `_status_tag`, `_CSS` and
  `render_surface`. The operator CSS is local to this page, so the public pages are
  byte-unchanged (tested).
- `tests/test_operator.py`: 13 tests, including byte-identity of the committed preview
  against a fresh render (decision D1).

## What it does not do yet

- No real client data. Pointing it at Client 1 means handing the loader that client's directory.
  If that directory has a different format, the loader adapts (D3).
- No actions: you cannot approve, send or reply from the page. It is read-only by design.
- No hosting or auth, and it is not in the published site.
- The nav links on the per-surface pages (Start here, Newsletters, ...) point at public
  pages that do not exist inside the preview folder, so they lead nowhere there.
- Newsletter cards on the Library board show the engine's existing placeholder ref ("NE")
  because the ledger does not carry issue numbers; the Editions list does show them.
- On a phone the edition status tag stretches full width (cosmetic).
- The client's real name is gone from current files but still exists in earlier commits on this branch (D6).
- No client-name filter for a real Library yet (D8).
- No CLI command; the preview is generated with the one-liner above.

## Three decisions for JJ to check (details in decisions.md)

1. **D1, tester sees what ships:** one renderer; the preview is its output; a test fails if
   the committed preview differs from a fresh render by one byte. This changes if the view
   needs live actions.
2. **D3, a client is a folder with `client.json`** (JSON, read-only, no new dependency).
   This changes if the real client already has its own format somewhere.
3. **D4, the meaning of Library, editions and interactions:** editions are dated issues
   pointing at a Library item; pending comes only from the interaction log and is never
   inferred from gate state.
