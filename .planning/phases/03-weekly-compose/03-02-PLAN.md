**Discretion exercised here, and why (log verbatim in the SUMMARY):**
- **Module layout:** `weeklyspec.py` sits beside `casespec.py`; there is no `assets.py` — every
  block sub-model already lives in `semantic.py`, and a separate module would have to stay
  semantic-free to avoid an import cycle for no gain.
- **The minter is PROMOTED, not forked and not privately cross-imported.** `pptx_writer.py` exists
  because two normalizers drift; two "pin a span honestly" implementations drift the same way. The
  promotion drops the leading underscore (`_SpanMinter` → `SpanMinter`, `_absent` → `absent`),
  following the `pptx_writer` promotion precedent: a name two modules import is not private. No
  test references the private names (verified against the live repo), so this is a safe rename.
- **Nested unknown keys fail loud too.** Rule 1 names the top level, but the same reasoning applies
  one level down: a mistyped `resaon:` inside a recognition would drop authored content silently.
  Same teaching voice, same refusal.
- **A recognition's `evidence` is a pointer, never an invented span.** When `source:` resolves to a
  known `Source`, `Recognition.evidence` holds one `Trace(source_id=<that id>)` with **no span** —
  the loader has not read that source's text and minting a span for it would be fabrication. When
  `source:` is absent *or* unresolvable, `evidence` stays `[]` plus its disclosure (weekly-spec
  rule 6 and the last routing row). The author's word is separately evidenced: `person` and
  `reason` are minted as gate-entailed `Claim`s at real spans of the spec file.

**The correctness condition, not a style preference:** `SpanMinter` is a forward-only cursor.
Walk `parsed.items()` and every nested collection in **document order**, and iterate each nested
mapping via its own `.items()` rather than a hardcoded field list — the author's field order is the
file's order. 03-RESEARCH proved by execution that minting a later field first silently swaps spans
for a value duplicated across two sections, and that **both claims still pass the faithfulness
gate** because the text is identical. No gate can catch this; only file order prevents it.

**Do not widen `casespec._validate`** to accept weekly keys — `docs/weekly-spec.md` lines 11-17
forbid it: each spec would silently accept the other's fields, destroying the strict-schema
teaching error in both directions.
