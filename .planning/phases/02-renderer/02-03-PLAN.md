Add a module-scoped `time_separated_renders` fixture to `tests/test_pptx_writer.py`. It builds the
rich template once into a `tmp_path_factory` directory, renders the same Draft sample Surface with
the same `RICH_SLOTS` twice, and **sleeps a real 3 seconds between the two renders**. Copy the
comment from `tests/test_pptx_determinism.py` explaining why the sleep is load-bearing: DOS
timestamps in a ZIP have 2-second granularity, so two writes inside one wall-clock second are
already byte-identical and a tight-loop test would "prove" a stability that does not exist. Module
scope so the suite sleeps once, not once per assertion. The fixture returns both the normalized
bytes and the un-normalized bytes for each render, because the negative control needs the raw pair.

To get the un-normalized bytes without duplicating the writer, have the fixture call
`render_surface_pptx_bytes` for the normalized pair and, separately, reproduce the raw pair by
invoking the same public entry point and reading the pre-normalization bytes — do this by rendering
normally and additionally saving a raw `prs.save(BytesIO)` of an identically-built presentation
inside the fixture. Whichever route is used, the raw pair must come from the same code path the
writer uses and must **not** be normalized; write a comment saying so, because a raw pair that
accidentally routed through the normalizer would make the negative control vacuous.

`test_double_render_is_byte_identical` — assertion **B**: the two normalized renders are byte-equal.
On failure, report `differing_parts(raw_a, raw_b)` and `differing_zipinfo_fields(raw_a, raw_b)` in
the message so a red diagnoses itself: a wall-clock timestamp, an unstable part order or an unstable
rel id leaking into the writer each show up in a different one of those two lists.

`test_unnormalized_double_render_is_not_byte_equal` — assertion **C**, the negative control. Assert
the raw pair is NOT byte-equal, that `differing_parts` is **empty** (the deck's content is
deterministic — only the container's clock moved), and that `differing_zipinfo_fields` is exactly
`["date_time"]`. Copy the failure-message style from the existing module: say that until this
inequality holds, the byte equality in `test_double_render_is_byte_identical` is not attributable to
the normalizer and proves nothing. This test is the one most likely to be deleted as "redundant now
that the writer exists" — the message must say that too.

`test_part_digest_is_stable_across_time_separated_renders` — assertion **A**, computed on the
**un-normalized** bytes: `part_digest(raw_a) == part_digest(raw_b)`. Comment that this is the
implementation-independent assertion Phase 4's committed==fresh gate inherits, because DEFLATE output
is zlib-implementation-dependent (zlib vs zlib-ng) and a full-file hash would be green locally and
red in CI with identical part content.

`test_rendered_archive_is_valid_and_normalization_is_idempotent` — reopen the normalized bytes with
`zipfile.ZipFile` and assert `testzip() is None`, that `[Content_Types].xml` is the **first** entry,
and that `normalize_opc_zip(normalized) == normalized`.

`test_fill_order_does_not_affect_output_bytes` — render once with `RICH_SLOTS` and once with the same
mapping in reversed key order, and assert the outputs are byte-identical (measured: text edits are
in-place on existing elements, so fill order is not a determinism variable — unlike image add order,
which is, and which Phase 3 pins to Weekly Spec file order).

Add a comment block at the top of this battery recording the constraint that governs every assertion
here: **no test may compare a rendered deck to the template** — not its bytes, not its `part_digest`,
not its part order. Opening the committed template and saving it unchanged already produces a
different `part_digest` (the `""`-valued core properties serialize as `<cp:keywords></cp:keywords>`
and come back as `<cp:keywords/>`), and part emission order differs between a built package and a
reopened one even when `_rels/.rels` is byte-identical. Both are properties of python-pptx's load
path, not regressions. Phase 4's golden deck must therefore come from the writer, never from
re-saving the template.
