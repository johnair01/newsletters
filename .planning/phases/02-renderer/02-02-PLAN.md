`_walk(shapes, group_type)` yields every shape in a shapes collection, **descending into groups**.
`bind_slots` does the single lazy `from pptx.enum.shapes import MSO_SHAPE_TYPE` (with the
`# noqa: PLC0415` comment and a note that it is lazy on purpose for the optional extra) and passes
`MSO_SHAPE_TYPE.GROUP` down, so the recursion predicate is measured rather than duck-typed and
there is exactly one lazy import per render. The recursion is load-bearing, not defensive:
`slide.shapes` is top-level only (measured, W17 — re-proved in this repo by
`test_group_nesting_hides_a_slot_from_slide_shapes`), so a `{sh.name: sh}` comprehension is blind to
a slot the operator can see in their Selection Pane, and the unfilled-slot check would never fire
for it. Grouping boxes is ordinary PowerPoint hygiene.

`bind_slots(prs, slots)` builds `{shape.name: shape}` across **every slide**, over `slide.shapes`
and not `slide.placeholders` (the latter holds only real placeholders keyed by `idx`; operator-added
textboxes and pictures are absent from it entirely). It then performs five refusals, in this order,
each raising `ValueError` with a three-part teaching message. Use RESEARCH §Pattern 2's drafted
texts — they are already in the house voice:

1. **Duplicate shape name** — raised while building the map, naming the duplicated name and telling
   the operator to rename one in PowerPoint's Selection Pane (Alt+F10). Duplicate names are legal in
   OOXML and copy-paste is how an operator makes one; last-wins would silently drop a slot, which is
   the exact failure D-03 exists to prevent.
2. **Template already defines `WATERMARK_NAME`** — the name is owned by the renderer, which adds the
   watermark itself; leaving it in the template produces two shapes with one name (measured: both
   are written, with no error) and defeats the binding map on the next render.
3. **Unknown content name** — every key of `slots` that is not in the map, sorted, named in the
   message, **with the sorted list of names the template does contain**, and the sentence that the
   renderer never invents layout.
4. **Unfilled reserved slot** — every name in the map that starts with `SLOT_PREFIX` and is not a key
   of `slots`, sorted and named; a reserved-prefix slot left empty would ship a blank box to a
   reader. The `NL_` prefix is what keeps this direction usable on a real deck — without it, every
   operator logo, footer and page number would be rejected.
5. **Slot cannot hold text** — for each key of `slots`, if the bound shape's `has_text_frame` is
   falsey, raise naming the slot and its `shape_type`, and say a group or picture cannot hold text
   so the operator should point the slot at a text box or place the content as an asset. Without
   this the caller gets `AttributeError`, a stack trace rather than a teaching error.

Add `fill_slot(text_frame, lines)` to `src/newsletters/pptx_writer.py`, implementing the
**reuse-and-clone** primitive from RESEARCH §Pattern 3. Carry that section's docstring reasoning
into the function docstring: python-pptx exposes **no bullet API** at all (`_Paragraph`'s public
surface is `add_line_break, add_run, alignment, clear, font, level, line_spacing, part, runs,
space_after, space_before, text`), so a bullet can only be *inherited*, never synthesized. Paragraph
0 of the template slot is the formatting carrier; every additional line is a deep copy of it with
its run's text replaced.

The algorithm: refuse an empty `lines` (an empty slot ships a blank box); take `text_frame.paragraphs[0]`
as `p0`; remove every paragraph after it via the lxml idiom `el.getparent().remove(el)` on `._p`;
refuse a `p0` with **zero runs** with the Pitfall 6 teaching error telling the operator to type one
character of placeholder text into the shape in PowerPoint and re-save the template (this is an
observed failure, not defensive padding: a text box with no typed characters really does have a
paragraph with zero runs, and there is then nothing to inherit from); remove every run after run 0
the same way; `copy.deepcopy(p0._p)` once per extra line, chaining each clone with `addnext` so
document order matches `lines` order; finally assign `paragraph.runs[0].text = line` pairwise.
`copy` is stdlib and may be imported at module level.

Comment the two rules the primitive encodes, because they are the ones a future editor will be
tempted to "simplify":
(a) **Never assign `text_frame.text` on an operator's shape** — measured to erase both the run's
`rPr` (20pt bold → `None`) and the paragraph's `pPr` (a `buChar` bullet vanishes), collapsing the
frame to one paragraph. The deck still renders, with the operator's formatting silently downgraded
to theme defaults — a visual regression no automated check in this repo can see except the fidelity
test added here. `tf.clear()` + `add_paragraph()` is only half-safe and is worse: it keeps p0's
`pPr` and loses every run's `rPr`, and added paragraphs get no `pPr` at all.
(b) **Never re-apply enumerated font properties after a `tf.text` assignment** — that copies only
the properties somebody thought to list; the deep copy carries the whole `rPr`/`pPr` subtree
including theme references and language tags.
Also state the standing ban: `TextFrame.fit_text()` must never be used anywhere in this module —
its `_best_fit_font_size` path locates a TrueType font file *installed on the current system*, which
would make output machine-dependent. It is the single most tempting non-determinism in the library.
Overflow is disclosed to a human, never "fixed" by shrinking the font (faithful, not suggestive).
